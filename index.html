Why This Matters to Me

From the patient side, eligibility, authorization, documentation, billing, and scheduling do not feel like separate departments. A problem in one part of the workflow can show up later as confusion or delay somewhere else. That connection is what I want to understand better.

Professional Transfer

A system can surface information. It cannot automatically prove that the information is current, authoritative, applicable, or sufficient for the next decision.

The same discipline supports my healthcare operations learning: inspect the evidence, identify the authoritative source, understand decision authority, assign ownership, act, and verify closure.

Portfolio Projects

These projects are how I turn coursework and independent study into visible practice.

Project 01

EVIS

Eligibility Verification Intelligence System

I built EVIS to practice identifying eligibility and intake issues earlier, before they have a chance to affect scheduling, authorization, claim readiness, or the patient's understanding of what comes next.

I am practicing: coverage verification logic, payer mismatch review, plan-type review, demographic conflicts, coordination-of-benefits risk, authorization triggers, exception ownership, escalation, closure verification, workflow gating, and clean intake readiness.

Live Site Exception Closure Control GitHub
Project 02

PARCS

Prior Authorization Command System

I built PARCS to explore how missing information, unclear ownership, aging requests, and escalation gaps can make a prior authorization vulnerable before the patient experiences the delay.

I am practicing: authorization tracking, documentation readiness, risk scoring, ownership review, escalation logic, aging visibility, and patient-access risk analysis.

Live Site GitHub
Project 03

DPIS

Denial Prevention Intelligence System

I built DPIS to work backward from denial risk and ask which upstream documentation, authorization, or claim-readiness problem could have been identified sooner.

I am practicing: denial root-cause analysis, documentation review, authorization-service matching, payer-rule awareness, claim-readiness thinking, and revenue-cycle workflow analysis.

Live Site GitHub
Project 04

SBI

Silent Breakpoint Intelligence

I built SBI around a question I keep coming back to: where did the workflow first lose control? The project helps me practice looking for handoff gaps and operational drift before the downstream problem becomes the only thing anyone can see.

I am practicing: breakpoint mapping, handoff review, workflow visibility, operational drift analysis, root-cause thinking, and dashboard communication.

Live Site GitHub

How to Review This Portfolio

If you are reviewing my work for a role, internship, networking conversation, or feedback, this path shows the progression I intended.

1. Start with EVIS

See how I approach eligibility and front-end patient access risk, then open the Exception Closure Control to see how I model ownership, escalation, closure verification, and the gate that prevents unresolved issues from moving downstream.

2. Move to PARCS

See how I think about prior authorization ownership, documentation, aging, and escalation.

3. Continue with DPIS

See how I connect upstream defects to denial and claim-readiness risk.

4. Review SBI

See how I map the first point of workflow control loss across handoffs.

5. Finish with Habit Audit

See how I evaluate recurring operational habits and improvement priorities across the workflow. The Streamlit demo may need a quick wake if idle.
